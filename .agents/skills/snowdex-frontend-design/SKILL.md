# SnowDex Frontend Design

## Контекст и решения

Прочитать [брендовые правила](../../../docs/brand-guidelines.md) и
[workflow](../../../docs/codex-design-workflow.md), соблюдая `AGENTS.md`.
Изучить продукт, данные, доменные types, presentation primitives и затронутый
путь. Не проектировать с выдуманным содержанием.

Сформулировать, что пользователь должен понять и сделать, затем выбрать
цельную visual thesis. Соотнести выразительность с доверием, читаемостью и
помощью выбору. Если направление свободно, сравнить разумные варианты и
выбрать самостоятельно; не требовать фиксированного числа вариантов.
Если направление задано, работать в нём. Итог принимает человек.

## Создание интерфейса

- Выбирать композицию, density, type, spacing, surfaces, responsive и motion
  по роли. Не повторять шаблон landing page на каждом экране.
- Подбор, каталог и detail могут иметь разную плотность с общим визуальным языком.
  Персональные причины fit не подменять характеристиками обычного каталога.
- Сохранять единицы, размерную identity, неизвестные значения, причины и
  ограничения. Не превращать unknown в уверенное утверждение.
- Переиспользовать подходящие компоненты; presentation refactoring допустим
  внутри scope. Данные, analytics wrappers и `/go/[slug]` сохраняются.
- Для повторяемых решений подключить
  [snowdex-design-system](../snowdex-design-system/SKILL.md) по необходимости.
  Не создавать полный kit заранее и не требовать отдельного handoff.
- Сохранять стек и server/client boundaries. Новые fonts, assets или dependencies
  обосновывать задачей, учитывать лицензию и стоимость; ничего не устанавливать
  автоматически ради визуального эффекта.
- Motion объясняет действие и состояние, уважает reduced motion и не задерживает
  задачу. Карточки и декор нужны, когда поддерживают смысл.

## Проверка и polish

Для большого редизайна проверять общий путь и все заявленные поверхности,
фазируя работу внутри одной задачи. Для локального изменения проверять
его состояния и влияние на общие компоненты.

Проверить отрисованный интерфейс на 390/768/1440 px и дополнительных ширинах
по контенту; клавиатуру, focus, увеличенный текст, touch и релевантные
loading/empty/error/risk состояния. Screenshots использовать для композиции,
браузерные действия — для поведения. Проходящий build не доказывает visual quality.

Исправлять обнаруженные проблемы и повторять затронутую проверку.
При недоступном браузере явно оставить rendered QA непроверенным;
не заменять его уверенностью по source code.

## Дополнительный reference

При пересмотре дизайн-инструкций или сравнении подходов читать
[external design research](references/external-design-research.md).
Для обычной frontend-задачи материал не обязателен. Внешние skills — источники
идей, а не разрешение менять контракты или выполнять external actions.
