# Weekly analytics recovery (048A)

GitHub Actions runs the existing Node.js reporting, digest and delivery modules directly. The job is restricted to protected main via the analytics-production environment. It does not call the Timeweb HTTP analytics endpoints. The Vercel configuration retains only the unrelated catalog-refresh cron. The current schedules are Monday 06:30 UTC (09:30 Moscow) for weekly delivery and daily 08:15 UTC (11:15 Moscow) for retry. A successful job or provider acceptance alone does not establish mailbox delivery.

## Before activation

1. Confirm the old Vercel scheduler is inactive and Timeweb's analytics email delivery flag remains false. Keep the GitHub analytics-production environment restricted to protected main. Requiring an approval on this shared environment would also pause every regular scheduled job. Use the explicit historical-recovery flag and per-week dispatch approval for historical delivery.
2. Configure the environment secrets ANALYTICS_DATABASE_URL and YANDEX_METRIKA_OAUTH_TOKEN and set YANDEX_METRIKA_ID to the reporting counter. Use the shared Supabase Session pooler on port 5432 with TLS and a dedicated role scoped to reporting reads and the existing delivery ledger. Verify GitHub-runner connectivity first in a non-production environment. Keep both delivery flags unset or false at this stage.
3. Run historical-audit individually for 2026-W44, 2026-W45 and 2026-W46 after authorized integration. It reads the exact weekly ledger identity and builds the existing digest from configured sources. It performs no ledger writes and does not initialize Resend. The result reports only safe statuses, identity and sampling classification. historical_sources_ready means the report passed the source and period checks. historical_already_sent requires a matching ledger period, acceptance timestamp and provider receipt. historical_ledger_exists requires owner reconciliation. An incomplete source must be investigated before recovery.
4. Preserve W43. In the 19 November read-only audit the ledger and an attached mailbox confirmed W43. W44–W46 were absent from the ledger and both searched mailboxes. First-party events were observed on all seven days of each missing period. This does not establish Metrika completeness or prove that Resend never accepted an email.
5. Before historical recovery, check each exact weekly report in Resend and the intended mailbox. A missing ledger row, missing inbox message or unavailable provider history is insufficient to exclude a prior send. If the outcome is uncertain, do not replay the week. Do not delete ledger rows, edit a digest, fabricate data or mark it sent to clear a gate.

## Historical recovery and first regular delivery

- Separately authorized historical recovery uses a manual workflow dispatch only. Keep ANALYTICS_DELIVERY_ENABLED false. Configure RESEND_API_KEY, ANALYTICS_DELIVERY_SENDER and ANALYTICS_DELIVERY_RECIPIENT in the protected environment. Verify the sender and exact intended recipient. Enable ANALYTICS_HISTORICAL_RECOVERY_ENABLED only for the approved recovery window. Select historical-recover with one exact week and confirm the prior provider check. Recover one week at a time and verify the durable accepted state and receipt containing the exact logical ID and period.
- The normal schedule never generates or retries W44–W46. The manual recovery is restricted to those three exact periods. It rechecks source quality and makes a create-only claim under the existing PostgreSQL advisory lock and unique identity. It never takes over an existing uncertain claim. The frozen reporting date is independent of the real lease and send timestamps. Redispatching an already accepted week sends no second email. A recovered claim that fails or terminates ambiguously needs manual provider reconciliation before further action. Disable the separate recovery flag once finished.
- If a W44–W46 report cannot be safely recovered, record the reason and supporting evidence in the owner's restricted release notes. With explicit owner approval set the protected environment variable ANALYTICS_HISTORICAL_NO_REPLAY. Use comma-separated entries such as `2026-W44:provider_unverified,2026-W45:sources_incomplete`. The only reasons are `provider_unverified`, `sources_incomplete` and `prior_delivery_confirmed` (confirmed elsewhere without a matching ledger receipt). Include only W44–W46. The workflow logs the unresolved ledger gap and the no-replay disposition. It cannot send a closed week, alters no ledger row, and preserves the distinction between confirmed delivery and closure. Removing a closure to reconsider recovery requires a separate owner decision and new provider/source evidence. W43 always requires ledger confirmation.
- After confirming W43 and resolving each of W44–W46 through an accepted ledger receipt or an explicit no-replay disposition, separately authorize setting ANALYTICS_DELIVERY_ENABLED=true. The next Moscow Monday may be allowed to run on its ordinary schedule, or use the weekly manual dispatch on that Monday for the immediately preceding ISO week. Verify the job result, ledger provider receipt and the intended mailbox. An accepted partial report stays clearly partial and cannot be silently replaced.
- If the first Monday job never created a ledger row, the same Monday's scheduled retry also checks and can run that week's ordinary delivery once. It uses the same reporting window and a create-only claim. Existing rows stay on the normal ledger retry and reconciliation paths. The operator can also use manual weekly dispatch before the Moscow 23:45 cutoff on that Monday. After the cutoff the ordinary workflow does not backfill. It logs missing recurring identities within the last 12 weeks and still generates the correct current week after initial reconciliation. Additional historical replay requires separate review. GitHub schedules may be delayed or skipped and workflow concurrency is not a durable queue.
- Expired claims, ambiguous provider responses, and transport failures require reconciliation. The retry sweep selects only due weekly rows from W47 onward and never hands unknown outcomes back to Resend. A definitive 429 can use the existing bounded retry policy and stored digest. Already accepted and active identities cannot be overwritten if report data later changes. Failure-notification emails and automatic ledger cleanup remain disabled for this workflow.

Weekly email includes the exact Moscow dates, Metrika users and visits, engagement and acquisition goal visits, and first-party funnel sessions and event counts. The attachment retains the validated privacy projection and sampling evidence. Missing first-party event days are disclosed and affected weekly numbers are omitted from the email summary. Event days are only a coverage signal. They do not prove continuous collection or unique visitor counts.

No production secrets, provider history, source exports, workflow activation or actual delivery are implied by local verification. See the [Supabase connection guide](https://supabase.com/docs/guides/database/connecting-to-postgres) and [GitHub Actions scheduled events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
