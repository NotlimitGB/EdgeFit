# EdgeFit UI System

Концептуальные правила интерфейса EdgeFit. Документ описывает роли, состояния
и поведение компонентов, но не требует создавать все перечисленные React-
компоненты заранее.

## 1. Назначение UI-системы

UI-система переводит бренд и visual direction в повторяемые решения:

```text
primitive tokens → semantic tokens → component tokens
```

Она должна:

- ускорять понимание результата;
- поддерживать путь от квиза к магазину;
- отличать рекомендацию от обычного каталога;
- сохранять mobile-first и accessibility;
- не раздувать проект абстракциями без повторного использования.

Новый компонент нужен, когда есть самостоятельная продуктовая роль, несколько
состояний или повторение. Одноразовый layout не обязан становиться primitive.

## 2. Базовые поверхности

Использовать ограниченный набор поверхностей:

- `page` — основной фон экрана;
- `section` — смысловой блок без обязательной рамки;
- `raised` — панель с ключевой информацией;
- `interactive` — clickable surface с hover/focus/active;
- `technical` — поверхность с метриками, сеткой или топографией;
- `warning` — локальное предостережение.

В dark alpine-контексте отделять поверхности контрастом, border и небольшой
глубиной, а не множеством blur/glow. Topographic lines и technical grid
оставлять фоновыми и некликабельными.

Предполагаемый `SectionShell` задаёт ширину, responsive padding и vertical
rhythm. Создавать его только при реальном повторении на нескольких секциях.

## 3. Кнопки и CTA

### Primary CTA

- Одно главное действие в смысловом блоке.
- На главной: «Подобрать доску».
- В recommendation card: «В магазин».
- Высокий контраст, видимый focus, touch target около 44 px.

### Secondary CTA

- Дополняет primary, но не конкурирует по цвету и весу.
- Примеры: «Смотреть каталог», «О модели», «Пересчитать подбор».

### Поведение

- Навигация — ссылка; submit/action — кнопка.
- Disabled и loading states сохраняют читаемую подпись.
- Store CTA всегда использует существующий `/go/[slug]` redirect и analytics
  wrapper, а не прямую внешнюю ссылку.
- Не размещать несколько визуально равных CTA рядом.

`PrimaryCta` и `SecondaryCta` являются ролями. Не создавать отдельный
компонент, если текущая архитектура лучше решает их повторяемым class pattern.

## 4. Карточки fit-параметров

`MetricCard` показывает один вывод:

- короткий label;
- крупное значение;
- единицу измерения рядом со значением;
- одно объяснение или контекст.

Приоритетные метрики результата:

- длина в сантиметрах;
- тип ширины;
- целевая ширина талии в миллиметрах;
- риск boot drag.

Карточки должны быстро сканироваться. Не помещать в них длинные абзацы и не
превращать все свойства результата в равнозначную сетку.

## 5. Product recommendation cards

`ProductRecommendationCard` отвечает «почему эта модель подходит этому
пользователю». Обязательные данные при наличии:

- brand и model;
- recommended size;
- роль: лучший общий, стабильнее, игривее, запас по ширине;
- confidence label или score;
- 2–3 причины совпадения;
- потенциальный минус или причина перепроверки;
- цена;
- CTA «В магазин»;
- вторичная ссылка «О модели».

Сначала показывать fit и причины, затем коммерческие данные. Не скрывать CTA,
но не делать цену главным аргументом рекомендации.

Вариант `avoid/careful` должен визуально отличаться от recommended, объяснять,
почему совпадение слабее, и не выглядеть равным лучшему варианту.

Recommendation card не заменяет `BoardCard` глобально. Каталоговая карточка
решает задачу обзора ассортимента, recommendation card — персонального выбора.

## 6. Fit badges

`FitBadge` — короткая смысловая метка:

```text
mid-wide
для all-mountain
мягче для новичка
стабильнее на скорости
запас по ширине
```

Правила:

- одна мысль на badge;
- короткий русский текст либо устойчивый snowboard-термин;
- не использовать badge вместо объяснения;
- ограничивать количество, чтобы сохранить иерархию;
- проверять перенос длинного текста на mobile.

## 7. Risk и warning states

`RiskBadge` и warning surface используют семантику:

```text
low = холодный нейтральный / спокойный
medium = amber / осторожность
high = amber stronger / warning, но без кислотного красного
```

Каждое состояние содержит:

- уровень словами;
- короткое объяснение причины;
- при необходимости действие: проверить ширину или размер.

Не кодировать риск только цветом. Красный сохранять для реальных ошибок формы
или критических системных состояний, а не использовать как декор.

## 8. Result summary

`ResultSummary` — первый содержательный блок `/result`. Порядок:

1. диапазон длины;
2. recommended width type;
3. target waist width;
4. boot drag risk;
5. shape profile;
6. краткое объяснение «почему так»;
7. переход к рекомендованным моделям.

Исходные параметры пользователя показывать вторично, чтобы подтвердить
контекст расчёта. Длинную логику и comparison details размещать после summary
или в progressive disclosure.

Empty state должен объяснять отсутствие результата и вести в квиз. Не
подменять реальный результат демонстрационными данными.

## 9. Catalog cards

Catalog card показывает:

- brand/model и изображение при наличии;
- форму, прогиб, стиль и ширину;
- доступные размеры и цену;
- переход к модели или магазину.

Она не должна:

- обещать персональное совпадение без квиза;
- показывать recommendation role;
- выглядеть сильнее result recommendation card;
- менять существующий tracked store path.

Глобальное изменение catalog cards требует отдельной задачи и проверки
каталога, board page и связанных SEO-страниц.

## 10. Mobile-first правила

- Проектировать сначала при ширине 390 px.
- Сохранять естественный DOM order: вывод → объяснение → модели → действия.
- Переводить метрики и cards в одну колонку без горизонтального scroll.
- Не делать sticky-элементы, перекрывающие контент или системную клавиатуру.
- Держать primary CTA рядом с соответствующим решением.
- Проверять длинные русские labels, цены, размеры и badge wrapping.
- На 768 px добавлять колонки только при сохранении читаемости.
- На 1440 px ограничивать line length и ширину контента.

## 11. Accessibility правила

- Контраст текста и интерактивных состояний — не ниже WCAG AA.
- Heading order отражает смысловую структуру.
- Все интерактивные элементы доступны с клавиатуры.
- `focus-visible` заметнее либо равен hover.
- Form label, hint и error связаны с control.
- Touch targets — около 44 × 44 px.
- Selected, risk, loading и error не обозначаются одним цветом.
- Декоративная графика скрыта от accessibility tree.
- Motion уважает `prefers-reduced-motion`.

## 12. Tailwind implementation notes

- Сначала найти существующие tokens, utilities и components.
- Избегать множества несвязанных arbitrary colors.
- Повторяемые semantic roles выносить в CSS variables, utility или небольшой
  component pattern.
- Изолировать alpine/dark styles wrapper-классом или локальным набором токенов.
- Не менять `:root` так, чтобы случайно перекрасить страницы вне scope.
- Использовать mobile-first responsive modifiers.
- Не добавлять dependency ради декоративного эффекта.
- CSS gradients, topographic lines и technical grid допустимы без assets.
- Heavy animation, CDN, новые fonts, canvas, WebGL и parallax требуют
  отдельного согласования.
