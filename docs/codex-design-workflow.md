# SnowDex — работа дизайн-агента

## Источники решений и routing

`AGENTS.md` задаёт инженерные границы. [Брендовые правила](brand-guidelines.md)
задают позиционирование и честность обещаний. Этот документ задаёт автономию
и критерии завершения. Skills дают прикладные инструкции:

| Запрос | Skill |
| --- | --- |
| Позиционирование, текст, CTA, обещания | [snowdex-brand](../.agents/skills/snowdex-brand/SKILL.md) |
| Art direction, UX, responsive, реализация и visual review | [snowdex-frontend-design](../.agents/skills/snowdex-frontend-design/SKILL.md) |
| Повторяемые tokens, компоненты и состояния | [snowdex-design-system](../.agents/skills/snowdex-design-system/SKILL.md) |

Выбирать минимальный набор. Нет обязательных последовательных handoff,
отдельной задачи на каждый экран или approval для каждого визуального решения.
Пользовательский brief определяет свободу; явно заданные решения сохраняются.

## Границы автономии

Человек задаёт продуктовую цель, брендовые и бизнес-границы и принимает итог.
Внутри разрешённого scope агент решает и объясняет существенные компромиссы.

| Уровень | Решения |
| --- | --- |
| Высокий | Композиция, группировка, иерархия, spacing, typography, surfaces, компонентное представление, локальная CSS-архитектура, responsive, micro-interactions, разумный presentation refactoring |
| С обоснованием | CTA wording, порядок вторичного содержания, progressive disclosure, page-level UX, добавление/объединение/удаление чисто презентационных секций; сохранить смысл, действия и факты |
| Только отдельный explicit scope | Recommendation/scoring, DB/schema/data/import, API/contracts, auth, analytics contracts, tracked redirects, commercial attribution, public URLs/SEO routing, продуктовые возможности и изменение фактических утверждений |

Обоснование не разрешает выход за scope. Page-level UX не включает изменение
вопросов, validation, вычислений или обязательных шагов квиза. Локальная задача
не разрешает глобально перекрашивать другие экраны. Большой публичный редизайн
может менять общие presentation primitives и каталоговые компоненты в своём
scope, сохраняя данные и поведение. Зависимость требует доказанной необходимости
и соответствия условиям задачи.

## Работа от миссии

Изучить текущий путь, реальные данные, компоненты, стили и интеграционные
границы. Для implementation осмотреть исходный интерфейс, если доступен.
Коротко сформулировать проблему, критерий успеха и visual thesis. Свободные
оси определить самостоятельно; заданную art direction сохранять, пока нет
конкретной причины предложить изменение.

Одна большая задача может охватывать `/`, `/catalog`, `/quiz`, `/result`,
`/boards/[slug]` и `/about`. Аудит и решения принимать для общего продукта.
Внутренне фазировать работу по primitives и пользовательским путям, сохраняя
целостность. Не сдавать половину продукта в новой системе без явно оговорённого
ограничения. Небольшому copy-edit нужен соразмерный процесс.

Создавать только необходимые общие правила и компоненты. Сохранять
Next.js/React/Tailwind conventions, server/client boundaries, доменные labels
и types. Отделять представление от вычислений; не дублировать расчёты в UI.

## Качество и проверка

Кодовые проверки и качество отрисованного интерфейса — разные доказательства.
Для UI implementation запускать проектные lint/test/build и `git diff --check`,
проверять затронутый путь в браузере и исправлять наблюдаемые проблемы.
Для docs-only достаточно `git diff --check` и `git status --short`.

Базовые ширины: 390, 768, 1440 px; добавлять промежуточные по контенту.
Проверять длинные русские подписи, реальные размерные labels, ошибки,
пустые/загрузочные состояния и различные количества результатов, где они
существуют. Не скрывать существенные действия ради узкого screenshot.

Доступность: семантика, клавиатура, видимый и не перекрытый focus, связанный
label/hint/error, контраст WCAG AA, увеличение текста и reflow, reduced motion,
смысл состояний вне одного цвета. Для частых touch-действий стремиться к 44 px;
не выдавать этот ориентир за универсальный норматив AA.

Осматривать screenshots и интерактивное поведение; исправлять clipping,
overflow, неясную иерархию и сломанные состояния. Использовать доступный browser
tooling без обязательной зависимости от плагина. Если браузер недоступен,
выполнить доступные проверки и назвать visual QA непроверенным; не заявлять
завершённое визуальное качество. Не использовать production формы,
пользовательские данные или тестовые analytics events для QA без разрешения.

Performance оценивать соразмерно media, fonts, client JS и motion.
Не заявлять измеренные показатели без измерений. Ошибки окружения отделять
от изменений.

## Сдача

Назвать результат, важные решения, файлы, проверенные пути/ширины/состояния,
команды и ограничения. Подтвердить сохранение инженерных контрактов.
Финальная продуктовая оценка принадлежит человеку; разрешение deploy/push/main
определяется задачей, а не workflow.
